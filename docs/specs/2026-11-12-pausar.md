# Pausar un run para darle el lugar a otro

Estado: diseño aprobado en la conversación · 2026-11-12

## Problema

Un repo tiene hasta `max_runs` runs trabajando (ADR 0019, 2 por defecto). Cuando se libera un lugar,
entra el run más viejo de la cola. No hay forma de darle prioridad a uno que está en cola: la única
manera de liberar un lugar es abortar un run, que borra sus worktrees, o esperar a que termine.

Pausar no es detener ni abortar:

- **detenido:** flowrunner se frenó por un problema y espera tu decisión;
- **abortado:** el run terminó y sus worktrees se borraron;
- **pausado:** lo decidiste vos. El run no tiene proceso ni lugar, conserva sus worktrees, su rama y
  todo lo hecho, y sigue cuando lo reanudás. Nunca vuelve solo.

## Decisión

Pausar espera a que el run termine lo que está haciendo: no se pierde trabajo. Al pausar elegís qué
run de la cola entra en su lugar.

Alternativas descartadas:

- **Pausar en el acto, cortando la sesión.** Libera el lugar enseguida, pero tira lo que hizo esa
  sesión y lo que costó. Queda para más adelante, si hace falta.
- **Que siga entrando el más viejo de la cola.** Pausar no serviría para elegir a quién darle lugar.

## El modelo

Dos eventos nuevos en `src/store/events.ts`, con `origen` opcional como las decisiones (ADR 0023):

```ts
{ tipo: "pausa_pedida"; at: string; para?: string; origen?: Origen }
{ tipo: "priorizado"; at: string; origen?: Origen }
```

Y un estado nuevo, `pausado`, en `RunStatus` y en todo lo que lo enumera: `contracts.ts`,
`watch/render.ts`, `notify/estado.ts` y `orca/src/runs.ts`.

### Reglas del reducer

1. **`pausa_pedida` con el run `en_curso`** no cambia el estado: suma `pausaPedida: true` al
   `RunState`. El run conserva su lugar hasta que para de verdad, así que nunca hay más de `max_runs`
   trabajando.
2. **`pausa_pedida` con el run `en_cola`** lo pasa a `pausado` en el acto: no tiene proceso que
   esperar, y sale de la cola.
3. **En cualquier otro estado** no hace nada. Esperando aprobación, detenido o con la PR abierta, el
   run ya no ocupa lugar.
4. **Al terminar una etapa** (`onOutcome`), el resultado se aplica como siempre. Si el estado que
   queda es `en_curso` y había `pausaPedida`, el run pasa a `pausado`, en la etapa que sigue. Si la
   etapa terminó en algo que te necesita (detenido, esperando aprobación, entregado), gana eso y la
   pausa se descarta: esos estados ya liberan el lugar.
5. **`reanudado` desde `pausado`** vuelve a `en_curso` en la misma etapa, como desde `en_cola`: sin
   reiniciar intentos ni vueltas. `pausaPedida` se borra.
6. **`priorizado`** no cambia el estado. Marca el run con la hora en que se priorizó.

### Implementar

Implementar puede durar mucho, así que la pausa se nota entre sub-tasks:

- Antes de arrancar una sub-task nueva, el planificador relee el log (como planificar con su
  `stateOf(readLog(...))`). Con `pausaPedida`, no arranca ninguna más, espera a que terminen las que
  corren (el mismo `Promise.all` que usa para un `fatal`) y devuelve un outcome nuevo, `pausa`.
- `onOutcome` con `pausa` deja el run `pausado` en implementar.
- Al reanudar, la corrida sigue la misma entrada (`currentEntry` trata `pausado` como `en_cola`): las
  sub-tasks integradas no se rehacen y las commiteadas se integran sin sesión nueva.

### La cola

`colaDe` (`src/store/runs.ts`) ordena primero los runs priorizados, del priorizado más reciente al más
viejo, y después el resto por antigüedad, como hoy. Un run que sale de la cola deja de estar
priorizado: el `priorizado` vale para una sola entrada.

`pause --para X` escribe `priorizado` en X junto con la `pausa_pedida`: cuando el run pausado suelta
su lugar, `despacharCola` despacha a X.

### Lo que no cambia

- `tick` reanuda solo `pausado_por_limite`. Un `pausado` no tiene `pausaHasta` y nunca vuelve solo.
- El proceso del run termina como siempre: `nextAction` da `fin` con un estado que no es `en_curso`,
  y el `finally` de `runProcess` suelta el lugar y despacha la cola.

## La CLI

- `flowrunner pause <run> [--para <run>] [--origen …]`:
  - con el run `en_curso`: «se pausa al terminar lo que está haciendo»;
  - con el run `en_cola`: lo pausa en el acto;
  - `--para` tiene que ser un run `en_cola` del mismo repo;
  - en otro estado: error que dice por qué no hace falta pausarlo.
- `flowrunner prioritize <run> [--origen …]`: el run tiene que estar `en_cola`.
- `flowrunner resume <run>` acepta también `pausado`, y entra a la cola si no hay lugar, como hoy.
- `status` y `watch` dicen «pausado», y un run `en_curso` con la pausa pedida dice «se pausa al
  terminar».

## watch --json

`RunTree` suma `pausaPedida?: true`. El recorrido suma dos pasos tuyos: «pausaste» y
«priorizaste».

## Orca

- **El menú ⋯ de un run que trabaja** ofrece «Pausar».
  - Con más de un run en cola en su repo, la tarjeta pregunta para quién es el lugar: un botón por
    run en cola, y «Cancelar».
  - Con uno solo, pausa con `--para` ese, sin preguntar.
  - Sin ninguno, pausa sin `--para`.
- **Mientras termina lo que hace,** la línea «ahora» dice «Se pausa al terminar lo que está
  haciendo», y el menú ya no ofrece «Pausar».
- **Un run pausado:** etiqueta «PAUSADO» en gris, «Pausado por vos» en la línea «ahora», y el botón
  «Reanudar». En el orden del panel va con los que están en cola.
- **El menú ⋯ de un run en cola** ofrece «Priorizar» y «Pausar».
- Las decisiones nuevas (`pausar`, `priorizar`) pasan por `decisionArgs` como comandos fijos, con
  el id del run validado y `--origen orca`.

## Tests

Cada test nuevo se ve fallar antes del código que lo pone en verde.

- `src/engine/engine.test.ts`:
  - pedir la pausa deja el run `en_curso`, y al terminar la etapa pasa a `pausado` en la siguiente;
  - una etapa que termina detenida o esperando aprobación gana sobre la pausa;
  - pedir la pausa en cola pausa en el acto;
  - `reanudado` desde `pausado` sigue en la misma etapa, sin reiniciar intentos.
- `src/store/runs.test.ts`: los priorizados salen primero; un run que salió de la cola deja de estar
  priorizado.
- `src/phases/implementar.test.ts`: con la pausa pedida no arranca sub-tasks nuevas, espera las que
  corren y devuelve `pausa`; al reanudar no rehace las integradas.
- `src/cli/tick.test.ts`: `tick` no reanuda un run `pausado`.
- `test/pausar.int.test.ts`, con `max_runs` 1 y dos runs en cola: pausar el que trabaja con `--para`
  el más nuevo hace entrar a ese y no al más viejo; reanudar el pausado lo deja en cola.
- `orca/src/runs.test.ts` y `orca/src/estado.test.ts`: las decisiones por estado, la pregunta de
  para quién es el lugar y la etiqueta de un pausado.
- `orca/src/worker.test.ts`: `pausar` y `priorizar` como comandos fijos, y un `--para` inválido no
  llega al shell.

## Fuera de alcance

- Pausar en el acto, cortando la sesión en curso.
- Pausar un run que no trabaja ni está en cola: no ocupa lugar.
- Ordenar la cola entera a mano: alcanza con priorizar uno.
